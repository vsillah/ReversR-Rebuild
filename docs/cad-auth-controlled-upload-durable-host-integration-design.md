## Candidate host and privileges

Propose a narrow authenticated service entry: an HTTP action verifies a separately approved host identity/channel, then calls fixed internal queries/mutations. No caller-selected function references, URLs, roles, identity headers or authority objects. The bridge carries a verified principal reference and generation; each mutation rechecks that principal's active scope and permitted operation in its own transaction. Review every internal call site. Exact issuer/audience/subject validation, signature/channel mechanism, key custody, propagation and revocation semantics remain unqualified. The upload bearer/cookie credential authenticates the user only; it is never host transport authentication.

Use distinct authenticated subjects and credentials for writer/recovery and independent reader/smoke roles; overlapping active subjects fail the independence check. Separate principals: grant custodian (install an approved immutable grant only), writer (forward operations only), recovery (close/revoke/mark unknown only), independent reader (receipt/authority readback only), and smoke verifier (bounded empty-request observation and evidence submission only). Neither writer nor recovery can create verifier evidence, restore authority, install grants or clear tombstones. An external smoke runner invokes only the exact approved endpoint after separate approval. Internal recovery scheduling remains bounded and separately authorized.

Use existing Convex/Auth authority tables for user/login/membership/session status. The new tables below hold upload-control records, not a replacement login system. All future functions need explicit argument/return validators and indexed bounded lookups. No unbounded scans. Add new tables; any changes to populated tables require optional-field migration and later validation, never an implicit destructive reset.

## Data and immutable grant

The adjacent JSON manifest is the exact proposed field/type/index contract (seven new tables). It contains no live grant values. `digest` means lowercase SHA-256, `uint` a nonnegative safe integer, `ref` a bounded opaque identifier, and `id(table)` a Convex ID. Optional values are explicit null. All fields are required; undeclared fields are rejected.

The grant custodian atomically installs the immutable grant and permanent unspent scope row before baseline verification, so its evidence can reference an existing scope ID. Scope registration seals the approved run and exact session without spending the attempt. Installation verifies independently approved source/custody records and existing user/login/session authority; it cannot create authority from caller assertions. The approved binding is installed once: resource, approved-run identity, cohort, deployment/commit/target/production alias, card and installation digests, durable evidence and service reference, upload credential digest, non-secret private credential supply requirement reference and private supply receipt digest, user/shop/login/upload session, route, finite window, IGES envelope digest and fixed ceilings. Both `sessionRef` (approved binding reference) and `sessionId` (authoritative session identity) must resolve exactly; one cannot substitute for the other. Every operation matches the full canonical binding digest and reads the immutable grant. Caller-supplied digests never establish approval. Grant bytes and approvals are reviewed separately before any installation.

`scopeKey = H(["controlled-scope-v1", resourceBindingDigest, cohortRef])`; `runKey = H(["controlled-run-v1", scopeKey, approvedRunId])`; `sessionKey = H(["controlled-session-v1", resourceBindingDigest, sessionId])`. H uses UTF-8 JSON arrays of validated strings in the stated order. Neither window, deployment nor card participates in singleton uniqueness. A permanently assigned scope row binds exactly one approved run and one session; the run slot and session tombstone cannot be freed, moved or recreated by changing hashes. A second run requires a different future approval and design; it is unsupported here.

Index names/columns are exact in JSON. Indexes are lookup paths, not assumed SQL uniqueness constraints. Every create reads the indexed range in the same transaction, takes at most two rows, rejects duplicates, and writes the scope singleton to serialize concurrent claims. The same rule applies to grant, principal, attempt, operation and evidence keys. Duplicate or corrupt rows stop the scope; no arbitrary first-row selection.

## Transaction and recovery contract

All forward mutations verify current host role, immutable binding, active user/login/membership/session generations, grant/scope revocation, trusted host time, expected revision and no permanent stop in the same transaction. The action cannot attest these on the database's behalf. No external effects inside mutations.

1. After atomic grant/scope registration, independently verify closed baseline and exact deployment/card binding before any claim.
2. `claimRun`: atomically spend the immutable scope run slot, reserve the exact session slot, create its permanent tombstone and attempt record, and create a recovery obligation. Losing workers stop.
3. `claimAttempt`: atomically spend the only attempt. `armRollback`: persist recovery duty before any fence can open. `openBodyAdmissionFence`: requires that duty and every forward check.
4. `consumeAttemptBeforeBodyRead`: atomically mark consumed and emit an application-owned operation receipt in that transaction. There is one eligible request nonce. An identical operation key can be read for diagnosis but never returns a fresh read permit. Request duplication/SDK reconnect cannot reauthorize the body.
5. Before subscribing to the body, the route must independently verify receipt, current authority and the time/stream guard described below. A lost, late, stale, mismatched or unknown response means zero body subscription, durable stop/recovery, and no retry. IGES validation remains bounded to 256 KiB source / 384 KiB JSON / 10 seconds, with the earlier grant deadline also enforced.
6. Close clears the fence; revoke increments authority generation and revokes the grant, upload session and late grants through the stable scope/session linkage. These restrictive transactions work after expiry and after a forward stop. They never clear spent/consumed/tombstone fields. A bounded independent recovery worker handles crashes; if the host is unavailable, the route stays closed and the obligation remains outstanding.

Transport, action and client forward retries are zero; no second upload. Provider-internal reexecution of a pure uncommitted transaction under OCC is a separate mechanism, not a second admitted attempt. The final result must still pass expiry/freshness checks. Unknown forward outcomes are never resubmitted. A separately authorized recovery worker may execute idempotent restrictive operations and readback under its own finite recovery budget; this is not upload retry or restored admission.

## Time, revocation and the stream boundary

Convex runtime `Date.now()` is frozen at function start (global scope time at deployment). It is not a commit timestamp. Store per-invocation `evaluatedAtMs`, and reject regression against persistent scope `lastHostTimeMs`; never use global-scope time or caller clocks as authority. Transaction latency can cross expiry. [Runtimes](https://docs.convex.dev/functions/runtimes)

A committed transaction and an HTTP stream subscription are not atomic. The candidate therefore **cannot yet satisfy strict admission safety**. Before runtime enablement, qualification must establish a trustworthy request-time UTC upper bound, bounded drift, monotonic elapsed-time guard and a reviewed revocation-to-stream handoff. Require `upperBoundNow < min(windowEndMs, sessionExpiry, grantDeadline)` after every await and synchronously before subscription; abort at/before that bound, before processing each chunk, and on invalid/regressing clocks. No awaited gap is allowed between the final guard and subscription. Delayed receipts are rejected even if their evaluation time was in-window. A timer alone is insufficient under event-loop stalls; platform/proxy prebuffering also needs explicit treatment.

A fresh readback still has a race with concurrent revocation. A lease does not meet a strict immediate-revocation requirement by itself. The exact linearization/hand-off protocol and trusted time guarantees are unresolved acceptance blockers. Until they are proved, keep the deployed terminal barrier, zero body subscriptions and no proof headers. This design does not redefine “no admission after expiry/revocation” as “transaction began earlier.”

Backup/restore can resurrect spent authority. Any restore, missing historical scope, lower revision/epoch or unverified custody continuity stops qualification. Reconcile against an independently retained approval/revocation/tombstone checkpoint before resuming control-plane access; a fresh empty database cannot authorize the old grant. No tombstone clearing or reissuing from stale backup is permitted. That checkpoint's custody and verification are also unqualified.

## Independent receipts, smoke and headers

Receipts have application-owned `operationKey`, sequence/revision and binding identity, written with the mutation. No native provider transaction ID is assumed or invented; `evaluatedAtMs` and Convex document creation time are not commit-time proof. The independent reader uses a separately authenticated read-only channel to compare receipt contents with committed rows, current scope/authority, exact request nonce and generation. Evidence must bind resource and deployed code identity. Self-reported `durable`, `expiryCheckedAtomically` or `independentEvidenceVerified` booleans are insufficient.

Convex now documents `ctx.db.vars.commitTs`, `v.commitTs()` and snapshot timestamps. Commit ordering can strengthen independent readback where supported; the placeholder is unavailable for an in-mutation expiry comparison and database timestamps must never be compared with `Date.now()` or `_creationTime`. These are ordering metadata, not an invented transaction identity. Local installed types at the repo-pinned Convex 1.45.0 expose `commitTs`; host support remains unqualified. The proposed nullable receipt ordering field requires independently read resolved values, otherwise remains null without an ordering claim. [Commit timestamp](https://docs.convex.dev/database/advanced/commit-timestamp)

Baseline and post-rollback evidence require a real independent empty unauthenticated `POST /api/cad/user-import`, exact deployed target/build, 401 `USER_SESSION_REQUIRED`, no controlled proof headers, plus host readback of fence closure, revoked session/late grants and retained tombstones. Source/route instrumentation must separately show zero body subscriptions/reads on denied paths, including revoked authenticated synthetic requests during qualification. A 401 alone proves neither revocation nor zero body reads. Smoke failure, missing readback, fabricated evidence or unknown cleanup makes outcome unknown; headers stay absent. No real smoke runs in this design turn.

Only a later separately qualified runtime may emit validation/rollback/card/install headers after the same request's valid IGES result, independently verified close/revoke and actual post-rollback smoke. Denied or uncertain outcomes emit none. Current `setControlledUploadValidationHeaders` boolean checks must be replaced or enclosed by a reviewed verifier-bound capability; this design does not claim that work is done.

## Custody, acceptance and next boundary

Keep credential values, CAD bytes, filenames, raw request/response bodies, tokens, personal identifiers and raw evidence out of logs, receipts and repository artifacts. Digests/session linkage are sensitive metadata: service-role access only, no public header exposure beyond already reviewed card/install digests. Proposed retention is 30 days for sanitized operation/smoke details, with zero raw-body retention. Minimal scope/session spent/revoked tombstones and independent continuity checkpoints persist for the lifetime of any possible replay; deletion requires a separate retirement design that permanently rejects the namespace. A retention approval is required before host use.

The manifest's finite acceptance matrix defines future independent-worker, restart, race, fault, clock, restore and forgery qualification. Its local tests only check that this design and its pinned sources have not drifted. No acceptance scenario is marked live-passed.

Next implementation boundary: review this contract; separately authorize source implementation of schema/bridge/state transitions/verifier interfaces and synthetic tests while retaining the terminal barrier. Before host qualification, provide approved resource/deployment and code identities, least-privilege principal/channel policy, independent verifier custody, clock/stream handoff design, recovery budget and restore/retention policy. Verify these through an independently approved qualification plan; return sanitized evidence references and digests, never credentials. Host access/configuration, paid use, real smoke, grant installation and activation each remain outside this design. No executable card, live window or live-opening approval phrase is issued.
