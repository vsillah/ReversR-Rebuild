## Google Cloud resource and custody plan - not provisioned

Implementer-owned recommendation: propose a new isolated ReversR custody project under an approved existing billing account, two private Standard-storage buckets (finite evidence details; enduring replay anchors), and a small authenticated Cloud Run custody service plus separately deployed independent reader. Region, project ID, bucket names, service URLs, retention durations and federation provider IDs are deliberately unbound. First verify project/billing permissions, organization constraints and named independent administrators. The existing Owner/Editor grants in the shared project must not be copied. Do not modify that project's IAM, federation or AI Studio bucket during this setup.

Use uniform bucket-level access with narrowly scoped IAM, public-access prevention, and no workload bucket/project administration or object deletion. Review inherited access as well as direct grants; public-access prevention is not a substitute for least privilege. [Storage IAM](https://docs.cloud.google.com/storage/docs/access-control/iam), [uniform access](https://docs.cloud.google.com/storage/docs/uniform-bucket-level-access), [public-access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention).

The custody service's dedicated runtime identity alone appends controlled records; the independent reader has read-only access. Writer, recovery, approval and smoke callers receive only their exact service operation permissions. Implementer must qualify the Vercel federation-to-Google identity-token exchange, exact receiving-service audience, invoker grant and application authorization; do not treat a raw Vercel token as a Google-signed Cloud Run ID token. The reader-to-Convex trust path and attestation policy also require implementation. [Cloud Run service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

Bucket Lock irreversibly prevents reducing/removing a locked retention policy, but object protection ends after retention; editable object metadata remains mutable. Place authoritative sequence, state, binding, nonce, policy and prior-anchor linkage inside retained payload bytes, not metadata. Lock only newly isolated buckets after explicit irreversible-action/retention-cost approval. Bucket Lock alone is neither a monotonic ledger nor permanent replay protection. [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock).

Required service behavior:

- Irreversibly reserve one-use approval/run/session identities behind the existing session fence. Payloads bind exact deployment, commit, command-card, installation, session, evidence and credential references/digests without secret values. Retain spent/revoked/unknown anchors and epoch/sequence history across Convex restore; never turn missing history into an unused slot.
- Return fresh authenticated high-water reads bound to the requesting operation, nonce and deployed policy; reject cached, replayed, lower-epoch, incomplete or unverifiable histories. A writer's own receipt or self-hash is insufficient.
- Write immutable per-sequence payloads using generation-match creation preconditions; pin generations on reads and condition any separate index updates. A zero-generation precondition checks absence of a live object, not absence of all history. Missing/noncurrent records must therefore trigger independent history reconciliation, never renewed authority. No multi-object atomicity is assumed; a mutable index is only a cache. Concurrent append, orphan append/index crash, stale generation, restore and lost response must fail closed as unknown without retrying the admitted operation. [Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).
- Deny destructive operations to workloads; verify payload generations, detect history/pointer regression, audit administration, and fail closed on inaccessible records, authentication, clock or custody service. Preserve an independently trusted namespace/epoch origin outside the Convex restore domain. An empty recreated bucket cannot become a new origin. Actual administrative independence and retirement enforcement remain qualification requirements.
- Approve retention duration, owner, cost and retirement procedure. Preserve minimal anti-replay anchors beyond evidence expiry for as long as any old grant could be presented; retire an authority namespace permanently before approved anchor deletion. Short-lived evidence retention must not silently erase spent history.

Finite evidence-detail retention and enduring replay anchors have separate policies. Evidence may expire after the approved review period; minimal anchors remain for the entire lifetime in which an old grant could be replayed. Retention expiry is never permission to clear spent state. Before retiring anchors, independently revoke and permanently reject the old namespace across every verifier, preserve that rejection beyond restore, and approve deletion after applicable retention. If that cannot be proved, retain anchors and budget their continuing storage. Existing Upstash, local files and the shared bucket establish no such guarantee.
