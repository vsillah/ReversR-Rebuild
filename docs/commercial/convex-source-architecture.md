# Commercial Convex source boundary

The commercial candidate will live in `commercial-backend/convex`, selected by that directory's own `convex.json`. It is a separate source assembly on the existing Convex stack. The root CAD `convex` assembly, its auth/schema/generated files, `server/index.js`, and existing digest-bound workflows remain unchanged. Deploying this candidate over the CAD deployment would replace its assembly and is prohibited. Selecting an approved deployment destination is a later architectural/operational gate; this task creates no project, account, deployment or service.

The candidate will register Convex Auth, ordinary Password sign-in/sign-up, its issuer configuration and HTTP auth routes. Backend operations will verify the SDK identity plus the current stored user and auth session. Email is profile data unless the auth user has a stored verification timestamp; it never links shops. New accounts own their own persistent shops. Billing ownership is checked independently of membership.

Commercial routes will select the Convex transport explicitly inside `server/commercialization.js`, preserving the existing registration in the protected `server/index.js`. The transport will forward the user's SDK bearer token to the configured Convex SDK endpoint. It will call bounded registered functions, never upload a JSON store snapshot. Missing configuration, unknown selectors, and non-integrated support/admin/native paths will deny access. Local file mode remains separately explicit for existing synthetic regressions.

Credits, period counters, retry keys, billing intents and processed Stripe event receipts will use indexed tables and transactional mutations. Only internal functions can change billing state. Provider actions remain configuration-gated; tests replace provider transport and use official `convex-test` for registered functions/schema. Such tests do not prove cloud OCC, persistence across host restart, provider configuration or deployed authentication.

The current workflow debits before provider work and does not bind follow-on requests to a server-owned journey. Refund, reservation and result-replay semantics require a product decision. The new transport will deny workflow execution while that policy remains unresolved, preserving existing catalog costs and calendar periods in the internal ledger implementation.

The Expo account surface will use the official SDK auth provider, propagate tokens to commercial requests, clear account state on logout/identity changes and reject stale in-flight responses. Local UI review will render actual components with synthetic auth/account adapters, with no provider connection. Legacy paid-account mapping remains a read-only migration requirement; no email/client-ID auto-linking or migration executes.
